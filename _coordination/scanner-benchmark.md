# Agent-package scanner benchmark and affordable product bar

Bridge goal **#57**, assignment **#59**. Research date: **2026-11-08**.
Owner: Codex; independent source research inputs from the Nadia/FinOps and Lena assurance roles.

**Recommendation:** build an accessible, local-first agent-package review workflow that combines instruction/code analysis, dependency intelligence and honest coverage reporting. Reuse established vulnerability data and interoperable formats; do not present a CVE lookup, keyword matcher, repository score or SBOM as a complete agent-security verdict. A useful base product must work without a paid model/API account.

This is a **documentation-based capability/cost benchmark**, not an executed performance comparison, certification, purchase recommendation or legal clearance. No competing scanner, package installer, malware sample, paid API or new account was run. Vendor capabilities are documented claims until reproduced on the same frozen corpus. Default-branch/latest documentation can describe unreleased behavior: choose and test an exact release before integration. Claude's #58 audit, not this report, establishes Injecticide's implementation gaps; #60 must turn the combined evidence into an agreed specification.

## 1. Compare the right layers

The user's actual artifacts include skills, Markdown instructions, scripts, references, embedded data and MCP configuration. Conventional npm/Python/container scanning is a necessary companion when those artifacts have dependencies, not a substitute for inspecting their instructions and behavior.

| Layer | What it can establish | What it does not establish |
|---|---|---|
| Agent-skill/instruction analysis | Evidence of override requests, secret disclosure, suspicious downloads, unsafe tool use, and the distinction between documentation/examples and active instructions | Universal intent detection, runtime enforcement or proof that an unflagged skill is safe |
| Code/content inspection | Script entry points, install hooks, interpreters, dangerous source/sink relationships, concealed executable content and inspection gaps | That every use of subprocess/network/base64 is malicious |
| Dependency SCA | Exact package/version or artifact matches against published affected ranges | Detection of all new malware, instruction attacks or undeclared dependencies |
| Package-malware intelligence | Matches to reported malicious package identities/versions and, where supplied, relevant hashes | A guarantee that unlisted or popular packages are benign |
| SBOM/provenance/repository posture | Inventory, artifact/build-origin evidence and repository-practice signals | A completed vulnerability scan or a benign-content certificate |

These boundaries inform the acceptance bar below; they are not assertions that Injecticide currently implements every layer.

### Explicit package types requested by David (#60 event 569)

| Package type | Inspection surface and benchmark interpretation |
|---|---|
| Skills | Instruction entry point, referenced text, scripts and bundled dependencies. Cisco Skill Scanner and Snyk Agent Scan are directly relevant comparators. |
| Plugins | Claude Code/Codex-style manifest, commands, agents, hooks, bundled skills and MCP configuration. Check schema and effective permissions plus every executable/instruction surface; schema validity alone is not safety. The sources reviewed do not establish complete end-to-end plugin coverage for either agent-native comparator. Measure each surface instead of claiming a plugin is covered because one bundled skill was scanned. |
| MCP server packages/configurations | Tool descriptions, transport/launch configuration, environment-secret references, source and resolved dependencies. Snyk Agent Scan supplies an agent-native comparator, with the discovery execution/cloud caveats below. Static inspection must not launch the target server. |
| Generated artifacts | HTML/JavaScript/TypeScript pages/apps, assets, package manifests and external references. Inspect browser-code risks, data flows, dependencies and declared remote capabilities; report unavailable remote content. Do not render/run an untrusted app during the static scan. Artifacts need code-security comparators as well as agent-instruction checks. |

**Artifact-code comparators:** [Semgrep CE](https://semgrep.dev/products/community-edition/) supplies local source analysis and JSON/SARIF, with no CE engine subscription fee. Its LGPL-2.1 engine license is separate from rule licenses: Semgrep-maintained rules have internal-use/competing-product restrictions, while third-party rules retain their own terms. **ESCALATE before bundling those rules in Injecticide**; own rules are an option, not proof of equivalent detection. [Licensing](https://semgrep.dev/docs/licensing). [CodeQL](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/) supports JavaScript/TypeScript analysis, but that does not establish complete HTML/DOM, arbitrary generated-app or prompt-injection coverage. GitHub code scanning is available for public repositories and eligible organization repositories with Code Security enabled; arbitrary private/commercial scanning entitlement and price are **UNKNOWN** here. [Availability](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning). Neither tool was executed. Parser, framework, inline-script and cross-file coverage must be tested on an exact pinned release; do not transfer paid-engine features to a free engine.

## 4. Free advisory data is not one blanket license

| Source | What it supplies | License / provenance requirement |
|---|---|---|
| **OSV aggregation** | Package/version, PURL/commit queries; batch IDs and modification times; record retrieval and ecosystem dumps. [API](https://google.github.io/osv.dev/api/), [batch contract](https://google.github.io/osv.dev/post-v1-querybatch/) | Code is Apache-2.0, but aggregated data retains source-specific licenses. The register includes CC-BY-4.0, CC0, Apache-2.0, MIT and restricted-source entries; an all-ecosystem dump is not automatically one redistributable license. [Source register](https://google.github.io/osv.dev/data/), [licensing explanation](https://google.github.io/osv.dev/data/new) |
| **GitHub Advisory Database** | CVE and GitHub-originated advisories in OSV records across covered ecosystems. [README](https://github.com/github/advisory-database/blob/main/README.md) | CC-BY-4.0. Retain required attribution/license information and identify modifications; do not claim endorsement. [License](https://github.com/github/advisory-database/blob/main/LICENSE.md) |
| **OpenSSF malicious-packages** | Reports of malicious package identities/versions, not a malware execution engine or general CVE source. [README](https://github.com/ossf/malicious-packages/blob/main/README.md) | Apache-2.0 in the repository and OSV source register. Preserve applicable license/notices and modification markings when redistributing. [License](https://github.com/ossf/malicious-packages/blob/main/LICENSE) |

OSV's current API documentation states no API rate limit, with a 32 MiB HTTP/1.1 response limit. That is not a purchased SLA or permanent quota promise. Batch results need pagination and follow-up record retrieval. Offline data needs recorded snapshot identity, update age, source licenses and withdrawal handling; a failed or stale feed is not a clean scan. [API contract](https://google.github.io/osv.dev/api/), [batch pagination](https://google.github.io/osv.dev/post-v1-querybatch/), [withdrawal/import behavior](https://google.github.io/osv.dev/faq/).

OpenSSF reports can include borderline/spam/typosquatting cases and acknowledge false positives. Optional file IoC hashes or imported report hashes must not be presented as the package archive's SHA-256. Preserve what each digest actually identifies. [IoC/origin schema](https://github.com/ossf/malicious-packages/blob/main/docs/schema_additions.md).

**ESCALATE before redistribution or hosted resale:** the chosen mixed-license data bundle's attribution/NOTICE packaging, any restricted sources, and commercial API-integration/content-sharing rights not established by public terms. This report records source terms; it does not grant legal approval. The initial corpus can use our own inert fixtures plus minimal, attributed advisory facts rather than mirror third-party code or redistribute whole datasets.

## 5. Standards and evidence roles

- **CycloneDX / SPDX:** interoperable component/dependency/security-information exchange. An exported document must validate against its declared schema/version and identify what was actually inventoried; generating it does not prove scanning occurred. [CycloneDX SBOM](https://cyclonedx.org/capabilities/sbom/), [SPDX overview](https://spdx.dev/about/overview/).
- **SLSA provenance:** artifact/build-origin evidence only when its binding, signature and trusted-builder policy are verified. Its presence does not establish harmlessness or absence of vulnerabilities. [Provenance](https://slsa.dev/spec/v1.2/provenance), [verification](https://slsa.dev/spec/v1.2/verifying-artifacts).
- **Scorecard / GUAC:** repository posture and evidence correlation respectively, not substitutes for these checks or formal product certification. Use them later if they solve an observed need, not to inflate a feature count.

## 6. Recommended minimum product bar for #60

These are **proposed acceptance requirements**, not universal industry pass percentages or claims of existing functionality.

| Must-have | Evidence required before a release claim |
|---|---|
| Safe artifact ingestion | No target installation, lifecycle hook, MCP server startup or embedded instruction execution during a static pre-install check. Enforce archive traversal/symlink, file-count, expanded-byte, recursion and time budgets; list unread content. |
| Correct identity and dependency inventory | Artifact digest plus source/registry identity, ecosystem, exact resolved version where known, lockfile origin and transitive coverage. Unsupported/unresolved dependencies remain explicit. A guessed version/name is not a confirmed affected package. |
| Layered agent-package detection | Paired active-instruction versus quoted defensive examples; file-role/context evidence; code/command/source-to-sink analysis where supported; concealed payload/encoding findings based on evidence, not a long URL alone. Separate facts from hypotheses. |
| Dependency and malicious-package intelligence | Known-affected and known-malicious matches recorded separately, with advisory IDs, affected-version evidence, feed/snapshot age and withdrawals. Heuristic typo similarity is a review signal, not proof of attack; dependency confusion needs trusted registry context. |
| Honest outcomes | Human-readable allow/warn/block with reason and evidence; separate assessment status/error/partial coverage. Never allow because a tool crashed, a database was absent, no packages were recognized, or output was truncated. Preserve the technical finding and the separate company-policy disposition agreed in #52. |
| Explainable policy exceptions | Trusted caller supplies policy outside the package. Named scoped exceptions, reason/approver/expiry, deciding mandatory rules and residual findings remain visible. Package content cannot authorize its own exception. |
| Useful automation | Versioned JSON schema; stable documented exit meanings; progress on stderr; verdict on stdout; timeouts; reproducible input/database hashes. The agent must check the exact bytes/identity subsequently installed, not a different artifact after the decision. A CLI/MCP endpoint alone does not enforce every install. |
| Accessible first use | One documented local command and one straightforward UI upload, no paid-model account required for the base scan, actionable explanation and concise/exhaustive exports. More optional engines must not force users to assemble a fragile command chain. |
| Measured quality | Freeze corpus/settings/tool versions; report per-category TP/FP/TN/FN, precision/recall/FPR and denominators, plus unsupported/timeout/error counts and runtime distribution. Keep training/tuning and held-out cases separate. Popularity is not a clean-package label. Synthetic inert fixtures test controls; they do not establish real-world malware recall. |
| Operational quality | Offline/cache behavior tested; stale/missing data distinct from no findings; no silent cloud upload; configured network consent and bounded costs. Authenticated provenance or a repository score cannot cancel a demonstrated content-level block. |

The corpus must cover benign security documentation, Confluence-style long URLs, legitimate scripts and network use as well as inert positive cases. Do not suppress false positives simply by trusting every reference-document path. #60 should choose numerical thresholds based on the product's risk tolerance and feasible labelled corpus; #59 does not invent an “industry-standard 99%” threshold.

Upstream result contracts also need explicit translation: Trivy defaults to exit zero even with findings; OSV documents separate general-error/no-packages exits. Do not equate another tool's exit zero with a complete company acceptance decision. [Trivy exit behavior](https://trivy.dev/docs/latest/configuration/others/), [OSV return codes](https://google.github.io/osv-scanner/output/).

## 7. Affordable operating model

Recommended base: local deterministic inspection, an explicit supported-input list, one reusable dependency-intelligence adapter/cache, interoperable output and clear coverage. Paid/model-assisted judgment is optional and separately budgeted; a local model is not zero-compute or guaranteed equal quality. Evaluate Cisco's agent-specific baseline alongside a dependency engine rather than rebuilding every source or calling a cloud model for every file. Do not run a GUAC cluster merely to scan one user's package.

No new vendor software subscription is necessary for the proposed base. That is **not a zero-total-cost claim**. Let N be monthly scans and T measured CPU seconds per scan:

`monthly operating cost = N*T/3600*CPU-hour rate + stored-GB*storage rate + downloaded-GB*network rate + optional model/service fees + maintenance effort`.

For an existing local machine the CPU-hour billing term may not apply, but electricity, hardware and support effort remain. No rates, scan times, token volumes or free allowances were measured for David's account, so an exact monthly bill would be fabricated. #61 must supply cold/warm-cache time and memory evidence; any paid activation remains a separate decision. Base-mode model API calls should be zero by design, not an unenforced budget reminder.

Privacy must be an operating choice: dependency identities can reveal proprietary inventory. OSV strict offline mode avoids project transmission; online lookups disclose query identities. Snyk Agent Scan v0.6+ transmits configurations/signatures and skill files with documented redaction. Socket's basic CLI documentation describes dependency-manifest transmission; Socket Firewall Free telemetry is always enabled and cannot be disabled; Enterprise telemetry is configurable. Do not market all these modes as local/private. [OSV offline](https://google.github.io/osv-scanner/usage/offline-mode/), [Agent Scan data flow](https://github.com/snyk/agent-scan/blob/main/docs/scanning.md), [Socket CLI privacy](https://docs.socket.dev/docs/socket-cli-faq), [Firewall Free](https://docs.socket.dev/docs/socket-firewall-free).
